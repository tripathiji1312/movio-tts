### 2026-09-04 — Aspect 2: Core technical approach / chunked TTS architecture (live sources)
**Subagent question:** What is the technically correct architecture to enable live/incremental streaming synthesis for IndicF5 (CFM-DiT, F5-TTS family) + Vocos vocoder — i.e., first audio chunk in milliseconds while the rest generates — and what options exist (syllable/prosody chunking, flow-step tuning, vocoder streaming, sentence-split streaming)? Must read movio/acoustic/ and movio/pipeline.py, fetch live docs: F5-TTS GitHub, ai4bharat/IndicF5 HF, Vocos streaming docs, chunked/streaming examples. Compare (a) sentence-split streamed synthesis, (b) true frame-level incremental DiT/vocoder streaming, (c) flow-step reduction/fp16/distilled steps.
**Answer:**
F5-TTS / IndicF5 is a **fully non-autoregressive (NAR) flow-matching CFM-DiT**: text is padded with filler tokens to the target mel length, then an ODE solver integrates noise→mel over NFE (`nfe_step`) function evaluations, then Vocos decodes the **whole mel in one forward pass**. Duration is estimated upfront from `ref_text_len/gen_text_len` ratio. This is why **true frame-level incremental DiT streaming (first audio in ~ms while DiT still denoising) is not architecturally possible without retraining**: DiT uses bidirectional self-attention + ConvNeXt text refinement over the full sequence, RoPE/conv positional embeddings, and adaLN-zero flow-step conditioning — every ODE step needs the whole utterance context.

So the technically correct production architecture is **chunk-level streaming ("first-chunk TTFA")**, not frame-level streaming:

#### Option (a) — Sentence / sub-sentence split + sequential streamed synthesis + crossfade [FITS THIS REPO — RECOMMENDED]
How it works: split text at clause/sentence boundaries → run one full `infer_process` (full NFE ODE + Vocos decode) per chunk → yield chunk 1 audio immediately while chunks 2..N synthesize → join with ~15–150 ms equal-power crossfade.
Pros: only officially supported streaming mode (upstream `chunk_text` + `infer_batch_process` with crossfade; Gradio/CLI "automatically do chunk generation for longer text"; socket server "chunk stream"); preserves prosody if chunks end at clause boundaries; TTFA drops from full-utterance cost to one-chunk cost; trivially parallelizable per chunk; works with frozen IndicF5 weights.
Cons: TTFA is still one full DiT pass (~1 chunk, hundreds of ms, not tens of ms); per-chunk ref-prompt conditioning resets prosody/timbre continuity — needs crossfade + fixed ref cache; too-small chunks hurt naturalness (duration estimator degrades, ref/gen ratio noise); total compute is same or higher (N chunks × NFE).
This repo already implements ~80% of it but **does not wire it to serving**: `IndicF5Engine.synthesize_stream()` (prosodic 8–14 syllable chunks + 20 ms crossfade) and `CascadedEngine.synthesize_stream()` exist, yet `TTSPipeline.stream_pcm_chunks()` synthesizes the **full utterance first, then slices PCM** — so measured TTFA = full latency, not first-chunk latency.
Correct wiring: 1. `stream_pcm_chunks` should call `engine.synthesize_stream()` and `yield float_to_pcm16(chunk)` per DiT chunk instead of buffering full audio. 2. Keep one-chunk lookahead: yield chunk 1 immediately; synthesize chunk N+1 while client plays chunk N (WebSocket `ws_chunk_ms=50` slicing stays as transport framing only). 3. Keep upstream defaults inside `infer_process`: sentence `chunk_text(max_chars≈135 / duration-derived)`, `cross_fade_duration=0.15`, `target_rms` normalization. 4. Keep single synthesis-worker queue but make it chunk-granular, or add per-sentence parallel workers only on GPU with VRAM headroom.

#### Option (b) — True frame-level incremental CFM-DiT + streaming vocoder [DOES NOT FIT — RESEARCH ONLY]
What it would require: (i) causal/block-causal DiT retrain or distillation so mel frames can emit before full text is integrated, + (ii) causal/streaming vocoder carrying ConvNeXt/ISTFT state across mel chunks with overlap-add.
Pros: genuine ~20–100 ms first audio; RTF decoupled from utterance length.
Cons: **incompatible with released IndicF5/F5-TTS weights** (bidirectional DiT, duration-known-upfront design); audible boundary artifacts without retrained causal attention + stateful vocoder; large engineering cost. Vocoder-side streaming alone does not fix DiT bottleneck — Vocos decode is already ~3–14 ms/chunk; DiT ODE is >90% of latency. Only adopt if prepared to train/fine-tune streaming variant.

#### Option (c) — Flow-step / precision / distillation tradeoff [FITS — DO FIRST, COMBINES WITH (a)]
Latency scales ~linearly with NFE. Knobs: `nfe_step` 32→16→8–12→7 (EPSS) ~2–4x speedup; paper 16 NFE RTF 0.15 WER 2.53 vs 2.42 at 32 NFE; EPSS 7 steps RTF 0.030 on RTX 3090 ~4x faster. `sway_sampling_coef -1.0` lets low NFE keep quality. `cfg_strength 2.0` lower slightly faster. `speed 1.0` >1 shortens duration but rushed prosody. `ode_method` euler=1 eval/step fastest; midpoint=2 evals (repo settings.yaml currently pays ~2x). `fp16/torch.inference_mode` typical ~1.3–1.8x on GPU if stable. Distilled/TRT-LLM runtime: upstream Triton+TRT-LLM RTF 0.040 vs 0.147 PyTorch at 16 NFE ~3.6x but requires NVIDIA GPU + export work.
